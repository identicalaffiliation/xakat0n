# Пользовательские сценарии: Кейс 2 «Авито Очередь»

## Зона ответственности

Мы отвечаем за то, кто прямо сейчас имеет право купить конкретный дефицитный товар и до какого момента это право действует. Саму оплату мы не проводим и не видим — платёжный сервис сообщает нам только исход попытки. Полный контекст окружающей системы — `baseline-system.md`.

## Портрет пользователя

«Охотник за дефицитом» — пользователь Авито, который давно ждал возможность купить конкретный редкий или лимитированный товар. Готов решать быстро, но боится не успеть из-за конкуренции с другими покупателями.

## Центральное обещание продукта

> **Дождались очереди — у вас N минут. Успели оплатить в это время — товар точно ваш.**

Из этой формулировки выводится вся механика, и её же можно показать пользователю дословно, без оговорок.

**Одно окно на весь путь.** Право на покупку — это право на окно времени, а не право на одно действие. Таймер выставляется один раз, в момент выдачи права, и дальше не меняется ничем: ни переходом к оформлению, ни попытками оплаты. Второй таймер, запускаемый нажатием «Перейти к оформлению», был бы хуже по трём причинам: он позволяет конвертировать остаток права в полное новое окно (значит, рационально жать кнопку немедленно, ничего не решая), обесценивает первый таймер и показывает пользователю два обратных отсчёта, второй из которых больше первого.

**Неудачная оплата не отбирает право.** Платёж не проходит чаще всего не по вине покупателя: лимит по карте, невыстоявший 3-D Secure, сбой эквайринга, сброшенное переключение в банковское приложение. Отбирать товар у человека, который честно отстоял очередь, за отказ его банка — это ровно тот несправедливый опыт, с описания которого начинается кейс. Поэтому внутри окна попыток оплаты сколько угодно.

**Слот освобождается ровно двумя способами:** истёк таймер или пользователь сам отказался. Больше ничем.

## Каталог сценариев

| № | Сценарий | Триггер / условие | Поведение системы | Категория |
|---|---|---|---|---|
| A1 | Обычный товар, без очереди | Товар не помечен как дефицитный (`is_limited = false`) | Кнопка «Купить» сразу ведёт к оформлению (заглушке); тикет очереди не создаётся, checkout пропускает без права | Демо |
| A2 | Вход в очередь — есть свободное место | free_slots > 0 в момент нажатия «Купить» | Тикет сразу создаётся в статусе OFFERED, выставляется `expires_at` | Демо |
| A3 | Вход в очередь — свободных мест нет | free_slots = 0 | Тикет создаётся в QUEUED, считается позиция в очереди | Демо |
| B1 | Переход к оформлению | В статусе OFFERED пользователь нажимает «Перейти к оформлению» | Тикет → CHECKOUT. `expires_at` **не меняется** — таймер общий на весь путь | Демо |
| B2 | Истечение права до оформления | Время вышло, оформление не начато | Тикет → EXPIRED; на ближайшем запросе к очереди этого товара следующий QUEUED → OFFERED | Демо |
| B3 | Несколько свободных мест сразу | Остаток товара > 1 | Столько же QUEUED-тикетов параллельно переводятся в OFFERED | Реализовать + тест |
| B4 | Оплата подтверждена | Платёжный сервис сообщает `paid`, тикет в CHECKOUT и не просрочен | Тикет → PURCHASED (терминальный), единица считается проданной | Демо |
| B5 | Оплата не прошла, окно ещё идёт | Платёжный сервис сообщает `failed`, `expires_at` не истёк | **Статус не меняется**, тикет остаётся в CHECKOUT, инкрементится счётчик попыток. Пользователь пробует снова — другой картой, другим способом, столько раз, сколько успеет | Демо |
| B6 | Окно истекло на этапе оплаты | `expires_at` прошёл, тикет был в CHECKOUT | Тикет → EXPIRED, слот уходит следующему. Сообщение отличается от B2: видно, что человек дошёл до оплаты и пытался | Демо |
| C1 | Товар раскуплен полностью, пока пользователь ждал | Число PURCHASED-тикетов сравнялось со stock | Все оставшиеся QUEUED-тикеты по товару разом переводятся в SOLD_OUT | Демо |
| C2 | Просмотр уже распроданного товара | Пользователь открывает страницу товара, весь сток продан | «Купить» неактивна, сразу видно «Товар распродан» + похожие лоты; встать в очередь нельзя | Реализовать + тест |
| C3 | Товар пополнили после SOLD_OUT | Продавец увеличивает stock уже после того, как часть тикетов стала SOLD_OUT | SOLD_OUT-тикеты остаются терминальными (не оживляем, не уведомляем); новые клики «Купить» от любого пользователя корректно видят свободные места | Реализовать + тест |
| D1 | Пользователь сам выходит | Нажимает «Отменить» в QUEUED или OFFERED либо «Отказаться от оплаты» в CHECKOUT | Тикет → CANCELLED. Из OFFERED и CHECKOUT слот освобождается в рамках того же запроса и сразу уходит следующему. Механика одна на все три статуса | Демо |
| D2 | Повторный вход при уже активной заявке | Снова жмёт «Купить», у него уже есть QUEUED / OFFERED / CHECKOUT тикет по этому товару | Новый тикет не создаётся — возвращается существующий | Реализовать + тест |
| D3 | Попытка обойти очередь | Прямой переход к «оформлению» без активного права на этот товар | Доступ блокируется (403) | Демо |
| D4 | Попытка переиспользовать / использовать чужое право | Оформление с терминальным тикетом (PURCHASED / EXPIRED / CANCELLED) либо попытка выдать себя за другого пользователя | Доступ блокируется. Переиспользование — потому что checkout сверяет статус и время; чужое право — потому что личность берётся из серверной сессии, а не из данных запроса | Демо |
| D5 | Двойной клик по «Купить» | Два одновременных запроса на создание тикета от одного пользователя | Проверка «уже есть активный тикет» + частичный уникальный индекс — создаётся только один | Реализовать + тест |
| D6 | Повторный вход после отмены или истечения | Пользователь жмёт «Купить» снова, имея тикет в терминальном статусе по этому товару | Создаётся новый тикет со свежим created_at — встаёт в конец очереди (или сразу OFFERED, если есть места) | Реализовать + тест |
| E1 | Возврат после разрыва сессии | Пользователь закрыл вкладку и вернулся позже | Статус подтягивается по паре (item_id, user_id); user_id восстанавливается из серверной сессии по токену в `sessionStorage` | Реализовать + тест |
| E2 | Никто не опрашивает статус | Все, кто мог продвинуть очередь, ушли со страницы | Продвижение зависает до следующего запроса кем угодно по товару. На корректность не влияет: обе финальные проверки сверяют время напрямую | Осознанно не в MVP — задокументированное ограничение |

## Живой демо-путь

A3 (второй и третий пользователь встают в очередь) → A2/B1 (первый получает право, переходит к оформлению, счётчик продолжает идти с того же места) → **B5 (у первого не проходит оплата — право при этом остаётся, он пробует снова)** → B6 (окно всё-таки истекает, единица возвращается в оборот, второй получает OFFERED) → B4 (второй оплачивает, PURCHASED) → C1 (третий видит «раскуплено» + похожие лоты).

Ветка про защиту показывается по ходу: D3 (переход к оформлению без права блокируется) и D4 (попытка воспользоваться чужим или израсходованным правом блокируется).

Пара B5 → B6 — смысловой центр демо. B5 показывает, что система на стороне покупателя: сбой платежа не стоит ему товара. B6 показывает вторую половину задачи из кейса: незавершённая покупка всё равно не держит товар вечно. Вместе они и есть обещание «успели оплатить — товар ваш», у которого обе границы честные.

Остальные сценарии (B3, C2, C3, D2, D5, D6, E1) — реализуем и покрываем юнит-тестами, в демо не показываем из-за ограничения по времени.

## Состояния заявки

```
QUEUED
  |-- есть свободное место -----> OFFERED
  |-- весь сток выкуплен -------> SOLD_OUT
  +-- пользователь отменил -----> CANCELLED

  ┌───────────────────────────────────────────────┐
  │  OFFERED и CHECKOUT живут под ОДНИМ дедлайном │
  │  expires_at, выставленным при выдаче права    │
  └───────────────────────────────────────────────┘

OFFERED
  |-- перешёл к оформлению -----> CHECKOUT   (expires_at не меняется)
  |-- время истекло ------------> EXPIRED
  +-- пользователь отменил -----> CANCELLED

CHECKOUT
  |-- оплата подтверждена ------> PURCHASED
  |-- оплата не прошла ---------> CHECKOUT   (остаёмся, попытка засчитана)
  |-- время истекло ------------> EXPIRED
  +-- пользователь отказался ---> CANCELLED
```

Терминальные состояния: `PURCHASED`, `EXPIRED`, `SOLD_OUT`, `CANCELLED`.
Слот товара занимают: `OFFERED`, `CHECKOUT`, `PURCHASED`.

| Состояние | Сообщение пользователю | Следующий шаг |
|---|---|---|
| QUEUED | «Вы N-й в очереди. Ближайшее место освободится не позже чем через MM:SS» | Ждать / выйти из очереди |
| OFFERED | «Товар ваш на MM:SS — успейте оформить и оплатить» | Перейти к оформлению / отменить |
| CHECKOUT | «Оплатите за MM:SS — это тот же таймер, он не сбрасывался» | Оплатить / отказаться |
| CHECKOUT после неудачной попытки | «Оплата не прошла. Попробуйте ещё раз или другой картой — у вас ещё MM:SS» | Повторить оплату / отказаться |
| PURCHASED | «Покупка оформлена» | — |
| EXPIRED, оформление не начиналось | «Время вышло, право на покупку истекло» | Вернуться к товару / встать в очередь заново |
| EXPIRED, оформление начато, попыток оплаты не было | «Время вышло, оплата не завершена — товар вернулся в продажу» | Вернуться к товару / встать в очередь заново |
| EXPIRED, попытки оплаты были | «Время вышло, оплата так и не прошла. Попробуйте другой способ оплаты» + похожие лоты | Встать в очередь заново / посмотреть похожие лоты |
| SOLD_OUT | «Товар раскуплен» | Посмотреть похожие лоты |
| CANCELLED | «Вы вышли из очереди» | Вернуться к товару |

Три варианта сообщения для `EXPIRED` различаются по полям `checkout_started_at` и `payment_attempts`. Последний вариант — небольшая, но честная работа на лояльность: человек видит, что система понимает, что он старался, и сразу получает альтернативу.

### Почему в QUEUED показываем верхнюю границу ожидания

Позиция считается только среди тех, кто ещё в QUEUED — держатели OFFERED и CHECKOUT в неё не входят, они ждут по своему таймеру. Без дополнительной подсказки пользователь видел бы «Вы 1-й в очереди» и минуту тишины: формально всё верно, но это ровно та «серая зона», которую кейс запрещает.

Поэтому рядом с позицией отдаём `next_slot_free_in_seconds` — минимальный оставшийся `expires_at` среди активных OFFERED и CHECKOUT по этому товару. Это не прогноз, а **гарантированная верхняя граница**: место освободится либо раньше (человек впереди купит или откажется), либо ровно в этот момент. Оценку «когда именно вы купите» не даём — она недостижима, потому что неизвестно, сколько человек впереди воспользуются правом, а сколько отвалятся.

## Сделанные допущения

- Дефицитный товар — флаг `is_limited = true`. Отдельного «порога дефицита» нет: если товар помечен лимитированным, очередь для него работает при любом остатке. Обычные товары очередь не запускают и checkout пропускает без права (A1).
- Момента «создания очереди» нет: каждый клик «Купить» заново вычисляет свободное место и либо выдаёт OFFERED, либо ставит в QUEUED. При остатке > 1 несколько пользователей получают право параллельно.
- Идентификация упрощена: `POST /auth/login` по имени пользователя выдаёт непредсказуемый `session_token`, сервер резолвит его в `user_id`. Клиент никогда не передаёт `user_id` — иначе подмена личности сделала бы бессмысленной всю защиту права (D4).
- Оплата вне скоупа. Платёжный сервис в MVP — заглушка, которая сообщает исход попытки (`paid` / `failed`). Наша ответственность — держать единицу занятой ровно на срок действия права и освободить её по истечении или по отказу пользователя.
- Число попыток оплаты внутри окна не ограничено — лимит противоречил бы самой идее «окно ваше». Ограничена только частота: не чаще одной попытки в 2 секунды, иначе кнопка «повторить» превращается в способ долбить бэкенд.
- Время действия права конфигурируемо и должно вмещать саму оплату: 10–15 минут для «продакшена», 60–90 секунд для демо. Это осознанная цена единого окна — быть скупым на этапе «подумай» и щедрым на этапе «заплати» больше нельзя.
- **Известное ограничение:** если пользователь запускает оплату за несколько секунд до конца окна и подтверждение приходит уже после `expires_at`, право считается истекшим, а `paid` отклоняется — возврат средств делает платёжный сервис штатным механизмом. Замораживать таймер на время попытки мы не стали: это открывает очевидную дыру (фиктивная попытка держит товар бесконечно), а безопасная версия — «одна заморозка, не дольше 120 секунд, только при зарегистрированной незавершённой попытке» — это отдельная подсистема со своими краевыми случаями. Вынесено в Could-have. На демо с 90-секундным окном и мгновенной заглушкой не воспроизводится.
- Правило очереди — простое FIFO по времени присоединения.
- Один пользователь держит только один активный (QUEUED / OFFERED / CHECKOUT) тикет на товар; на разные товары — без ограничений.
- Терминальные статусы не оживляются автоматически — ни при повторном интересе пользователя, ни при пополнении стока. Обратный путь только один — новый клик «Купить», создающий новый тикет в конце очереди (D6).
