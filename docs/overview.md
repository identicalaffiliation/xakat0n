# Авито Очередь — Кейс 2, Avito Start

MVP сервиса пользовательской очереди для дефицитных товаров: пользователь встаёт в очередь, получает временное персональное право на покупку, система защищает от одновременной продажи одной единицы товара нескольким покупателям.

Инструкция по запуску — в корневом `README.md`. Здесь — карта документации и ключевые решения.

## Зона ответственности

Мы отвечаем за то, кто прямо сейчас имеет право перейти к оформлению покупки конкретного дефицитного товара, и до какого момента это право действует. Регистрация, оформление заказа, оплата и списание стоков — уже реализованы в реальном Авито и вне скоупа кейса; в MVP это заглушки. Как именно устроена реальная система вокруг нас — `baseline-system.md`; наши сценарии поверх неё — `demo-scenario.md`.

## Ключевые решения одной строкой

- **БД: PostgreSQL, не Redis** — атомарность через `FOR UPDATE`/`SKIP LOCKED`, персистентность из коробки, не нужен второй stateful-компонент (`architecture.md`)
- **Обновление статуса: polling, не WebSocket** — сохраняет естественный триггер для `advanceQueue`, не добавляет управление жизненным циклом соединений (`architecture.md`)
- **Идентификация: заголовок `X-User-Id` + login по username, не cookies** — куки шарятся между несколькими одновременно открытыми окнами инкогнито, что ломает демо-сценарий с несколькими параллельными пользователями (`api-contract.yaml`)
- **Право на покупку — временное, персональное, одноразовое.** Не путать со статусом оплаты: мы не видим и не отслеживаем оплату, наша ответственность заканчивается в момент `COMPLETED`
- **`internal/queue` — один владелец**, не разбит на подмодули: create/advance/cancel используют общую логику подсчёта свободных мест, искусственное разделение создало бы постоянную стыковку

## Ограничения MVP (Won't have)

Полноценная регистрация, реальное оформление заказа и оплата, списание стоков, email/push-уведомления — все осознанно исключены, обоснование в `baseline-system.md`.
